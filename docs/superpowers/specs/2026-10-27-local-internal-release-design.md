# KimiCodeBar 独立定制版开发与发布基线设计

## 项目目标

以作者当前开源代码为基础，建立一个由使用者长期独立维护的 KimiCodeBar 定制版。项目的主要工作是根据自身需求直接增加功能、调整计算逻辑和修改文案，而不是持续跟随或合并原作者更新。

当前这份设计只处理支撑后续定制开发的基础链路：Xcode 可直接打开运行，本地可生成 Ad Hoc 签名 DMG，GitHub Actions 可在推送版本标签后自动生成供同事下载的 DMG。具体新增功能将在后续逐项设计。

## 约束

- 不购买或使用 Apple Developer 付费证书，不做 Apple 公证。
- 不改变现有 CPU 架构配置，不额外兼容作者未兼容的芯片。
- 新功能继续采用作者的 Swift / SwiftUI 技术栈、UI、交互和双语文案风格，不做界面重设计。
- 功能与文案直接修改或接入现有代码，不设计插件或运行时嵌入机制。
- App 不连接原作者更新源，作者后续发布不会自动覆盖或改变这个定制版；是否手动参考上游代码由使用者另行决定。
- 不分发本机账号数据，不读取或提交任何凭证文件。
- 本次不递增版本号、不创建发布标签，只搭好基础链路并验证。

## 方案比较

### 方案一：保留作者发布流程并新增并行流程

通过仓库归属保护让作者流程只在原仓库运行，再新增定制版流程。它适合需要持续同步上游的 Fork，但会保留不再需要的证书、公证和上游发布配置，不符合长期独立维护的目标。

### 方案二：建立独立定制版的单一发布流程（已按修订目标选择）

将现有发布 Workflow 直接简化为定制版自己的 Ad Hoc DMG 发布流程，删除不再需要的付费证书、公证、Sparkle appcast 和上游 Pages 发布步骤。项目只保留一套发布入口，结构更直接，也不再围绕上游同步做兼容设计。

## 设计内容

### 独立源代码基线

当前 Fork 的 `origin` 作为项目唯一远程仓库，不配置自动同步上游的机制。后续功能与文案直接演进这份代码，作者更新不会自动进入项目。

### 本地构建

新增 `scripts/build-local.sh`，从仓库根目录执行 Release 构建，使用 Ad Hoc 本地签名，校验 App 签名，生成包含 App 与 Applications 快捷方式的 DMG。构建产物放在忽略提交的目录中，脚本面向用户的消息使用中文。

### GitHub 发布

把现有 `release.yml` 简化为定制版发布流程：推送 `v*` 标签时运行同一套本地打包逻辑，并将 DMG 上传到当前仓库的 GitHub Release。不执行 Developer ID 签名、公证、Sparkle appcast 或上游 Pages 部署。

### 更新行为

彻底停用上游自动更新：启动、打开面板和手动刷新都不会读取上游 appcast 或启动 Sparkle 更新检查。保留现有版本显示和 UI，不新增更新设置页。定制版通过重新构建和分发 DMG 更新。

### 使用说明

在现有中英文 README 中补充简明说明：如何用 Xcode 打开运行、如何执行本地 DMG 打包、GitHub 标签发布行为，以及同事首次打开未公证 App 时需要在 macOS「隐私与安全性」中允许。

## 验证

- 执行项目现有 Debug 编译，确认源码仍可由 Xcode 工具链构建。
- 实际运行本地打包脚本，确认生成 Release App 和 DMG，且签名为 Ad Hoc。
- 检查 DMG 内容，确认只包含应用与安装快捷方式，不含账号数据。
- 打开 Xcode 工程并运行开发版，确认菜单栏应用可启动。
- 检查 Git 工作区，确保构建产物未被提交。
- GitHub Actions 的真实标签发布留待首次正式发版时验证；本次不为了测试擅自递增版本或创建标签。
