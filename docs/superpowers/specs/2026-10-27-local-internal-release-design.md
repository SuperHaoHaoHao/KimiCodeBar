# KimiCodeBar 本地开发与内部发布设计

## 目标

让没有 Swift 开发经验的使用者也能维护自己的 Fork：源码可由 Xcode 直接打开运行，本地可生成 Ad Hoc 签名 DMG，GitHub Actions 可在推送版本标签后自动生成供同事下载的 DMG。

## 约束

- 不购买或使用 Apple Developer 付费证书，不做 Apple 公证。
- 不改变现有 CPU 架构配置，不额外兼容作者未兼容的芯片。
- 不改变作者的 Swift / SwiftUI 技术栈、UI、交互和双语文案风格。
- 功能与文案后续直接修改或接入作者现有代码；独立仅指发布流程，不设计插件或运行时嵌入机制。
- 不分发本机账号数据，不读取或提交任何凭证文件。
- 关闭 Fork 版本的上游自动更新，防止定制版本被上游覆盖；本次通过重新构建 DMG 更新。
- 本次不递增版本号、不创建发布标签，只搭好链路并验证。

## 方案比较

### 方案一：独立内部发布流程（已选择）

新增本地打包脚本和内部 GitHub Actions Workflow，原作者正式发布流程保留并仅在原作者仓库执行。优点是你的发布配置与作者分开，后续同步上游时冲突较少。

### 方案二：改写原作者发布流程

直接删除原流程中的证书、公证与 Sparkle 发布步骤。文件更少，但与上游差异较大，后续同步冲突和维护成本更高，因此不采用。

## 设计内容

### 本地构建

新增 `scripts/build-local.sh`，从仓库根目录执行 Release 构建，使用 Ad Hoc 本地签名，校验 App 签名，生成包含 App 与 Applications 快捷方式的 DMG。构建产物放在忽略提交的目录中，脚本面向用户的消息使用中文。

### GitHub 内部发布

新增独立 Workflow，在推送 `v*` 标签时运行同一套本地打包逻辑，并将 DMG 上传到当前 Fork 的 GitHub Release。不执行 Developer ID 签名、公证、Sparkle appcast 或上游 Pages 部署。

原作者 Workflow 增加仓库归属保护，只在 `xifandev/KimiCodeBar` 执行，避免 Fork 打标签时因缺少原作者证书和 Secrets 而失败。

### 更新行为

将 Fork 的更新检查设为默认关闭，并确保启动、打开面板和手动刷新都不会读取上游 appcast 或启动 Sparkle 更新检查。保留现有版本显示和 UI，不新增更新设置页，不改变作者界面。

### 使用说明

在现有中英文 README 中补充简明说明：如何用 Xcode 打开运行、如何执行本地 DMG 打包、GitHub 标签发布行为，以及同事首次打开未公证 App 时需要在 macOS「隐私与安全性」中允许。

## 验证

- 执行项目现有 Debug 编译，确认源码仍可由 Xcode 工具链构建。
- 实际运行本地打包脚本，确认生成 Release App 和 DMG，且签名为 Ad Hoc。
- 检查 DMG 内容，确认只包含应用与安装快捷方式，不含账号数据。
- 打开 Xcode 工程并运行开发版，确认菜单栏应用可启动。
- 检查 Git 工作区，确保构建产物未被提交。
- GitHub Actions 的真实标签发布留待首次正式发版时验证；本次不为了测试擅自递增版本或创建标签。
